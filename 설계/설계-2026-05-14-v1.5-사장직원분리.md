## 1. 배경

지금까지 「사장님 단일 사용자」 가정으로 모든 페이지가 동일 권한이었음. 하지만 실사용 시나리오는 두 갈래:

- **사장님 (Owner)** — 본인 노트북/모바일에서 로그인. 매출·인건비·정산 등 운영 데이터 풀 접근.
- **직원 (Staff)** — **매장에 비치된 iPad/PC** 공유 단말에서 사용. 출퇴근 펀치, 업무 보고, 본인 근무표 확인. 직원끼리 근무표 협의·교대 신청도 여기에서.

이 분리 없이는 「매장에 iPad 놓고 직원이 사용」 시나리오에서 사장 권한 데이터(급여·매출·다른 직원 시급)가 노출됨. SaaS 확장 시도 차단 요소.

## 2. 핵심 결정 — 사용자 확정 (2026-05-14)

| 결정 항목         | **확정안**                                | 근거                                   |
| ------------- | -------------------------------------- | ------------------------------------ |
| **인증 모델**     | **사장님 계정 + 매장 계정 각 1개 (총 2개 Auth 계정)** | 로그인 페이지에서 「사장님 / 매장」 분기. PIN 모델 폐기   |
| **로그인 진입점**   | **/login에 「사장님 로그인 · 매장 로그인」 탭 분리**    | 매장 단말은 매장 계정으로 한 번만 로그인해두면 됨         |
| **권한 계층**     | **owner / store 2단계** (매니저 분리 없음)      | 매장 계정으로 들어오면 누구든 매장 화면 내 수정 가능       |
| **매장 모드 토글**  | **불필요 — 계정 자체가 매장용**                   | localStorage flag 등 별도 메커니즘 제거       |
| **체크리스트 처리**  | **즉시 폐기 → 신규 「업무(Tasks)」로 대체**         | 기존 데이터 이관 없음. 깨끗하게 시작                |
| **다중 매장**     | **지원** — 사장님 1명이 매장 N개 운영 가능           | 사장 계정 ↔ stores N개, 매장 계정 ↔ store 1:1 |
| **푸시/SMS 알림** | **본 작업 범위 외 — 추후 별도 Phase**            | CLAUDE.md 미결사항으로 명시                  |

### 모델 다이어그램

```
사장님 계정 (Auth user, owner)
  ├── 매장 A (stores.owner_id)
  │     └── 매장 계정 A (stores.store_account_user_id → Auth user)
  ├── 매장 B
  │     └── 매장 계정 B
  └── 매장 C ...

각 매장 단말 = 해당 매장 계정으로 로그인
```

## 3. 사용자 페르소나

### 사장님 (Owner) — Auth 계정 1개
- 출현 빈도: 매일 1~3회 (출근 전, 점심, 마감 후)
- 디바이스: 본인 노트북/스마트폰
- 핵심 관심: 인건비·매출·이상치(지각·휴무 부족)·이번 달 정산
- **읽기 위주 + 월말 정산 작업**
- 다중 매장 보유 가능 — UI 상단에 매장 셀렉터

### 매장 (Store account) — 매장당 Auth 계정 1개, 직원 공유
- 출현 빈도: 영업 시간 내내 (매장 단말 상시 로그인)
- 디바이스: 매장 비치 iPad/PC
- 핵심 관심: 출퇴근 펀치·오늘 업무 진행·근무표 조정
- **매장 화면 내 모든 데이터 수정 가능** (매니저 권한 분리 없음)
- 사장님 데이터(급여·정산·매출) 접근 불가 — RLS로 차단

**보고자 식별**: 매장 계정은 공유 계정이므로 「누가 했는지」 트래킹은 **보고 등록 시 staff 드롭다운 선택** 방식. `store_task_reports.staff_id`로 기록.

## 5. 데이터 모델 변경

### 5-1. `stores` 테이블 확장 — 매장 계정 연결

```sql
ALTER TABLE stores ADD COLUMN IF NOT EXISTS store_account_user_id uuid
  REFERENCES auth.users(id) ON DELETE SET NULL;
CREATE INDEX IF NOT EXISTS stores_store_account_user_id_idx
  ON stores(store_account_user_id);
```

- `store_account_user_id`: 매장 계정의 Supabase Auth user.id. 매장당 1개.
- 매장 계정은 사장님이 「매장 정보」 → 「매장 계정 만들기」에서 email+비밀번호로 생성 (Supabase admin API 또는 Edge Function).
- PIN/role 관련 컬럼은 추가 안 함 — 매장 계정 = 매장 전체 권한 단일.

### 5-2. 신규 테이블 — 업무 (Tasks)

```sql
CREATE TABLE store_tasks (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id uuid NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  category text NOT NULL CHECK (category IN ('open', 'middle', 'close', 'weekly', 'monthly', 'other')),
  title text NOT NULL,
  description text,
  description_images text[],            -- Supabase Storage path들
  /** 보고 방식 — 셋 중 1개 또는 조합 */
  report_type text NOT NULL CHECK (report_type IN ('check', 'photo', 'memo')),
  /** 반복 주기 */
  recurrence_type text NOT NULL CHECK (recurrence_type IN ('daily', 'weekly', 'monthly', 'once')),
  /** weekly 시 1~7 비트마스크 또는 요일 배열 (0=월) */
  recurrence_days integer[],            -- ex: [0,2,4] = 월수금
  /** monthly 시 일자 (1~31) */
  recurrence_day_of_month integer,
  active boolean NOT NULL DEFAULT true,
  display_order integer NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE store_task_reports (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id uuid NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  task_id uuid NOT NULL REFERENCES store_tasks(id) ON DELETE CASCADE,
  staff_id uuid NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
  work_date date NOT NULL,              -- 어느 날짜의 보고인지
  reported_at timestamptz NOT NULL DEFAULT now(),
  /** report_type에 따라 채워지는 필드 */
  checked boolean,                      -- check 보고
  memo text,                            -- memo 보고
  photo_urls text[],                    -- photo 보고 (Supabase Storage path)
  UNIQUE(task_id, staff_id, work_date)  -- 동일 날짜·동일 직원 중복 방지
);
```

RLS:
- Owner: 본인 매장 모든 row CRUD
- Staff/Manager: 본인 매장 `store_tasks` 읽기. `store_task_reports` — 본인 row만 CR (수정·삭제 ✗, 매니저는 매장 전체 R)

### 5-3. Supabase Storage 버킷

```
gelato-os-storage/
  tasks/{store_id}/{task_id}/description-{n}.jpg    -- 업무 설명 이미지
  tasks/{store_id}/{task_id}/{report_id}/{n}.jpg    -- 사진 보고
```

- 버킷 정책: `store_id`가 본인 매장이면 R/W
- 이미지 크기: 클라이언트단 리사이즈 (max 1024px, JPEG q=80) → 평균 100~200KB

## 6. 라우트 구조 + 진입 분기

### 로그인 페이지 — 「사장님 / 매장」 분기

```
/login
  ┌──────────────────────────────┐
  │  [ 사장님 로그인 ]  [ 매장 로그인 ]  │  ← 탭
  │  ────────────────────────    │
  │  Email                       │
  │  Password                    │
  │  [ 로그인 ]                   │
  └──────────────────────────────┘
```

- 탭 선택 → 동일 폼이지만 로그인 후 분기 처리
- 「사장님 로그인」: Auth 통과 후 `app_metadata.account_type === 'owner'` 검증 → `/` (Owner 대시보드)
- 「매장 로그인」: Auth 통과 후 `app_metadata.account_type === 'store'` 검증 → `/store/home`
- 다른 종류 계정으로 잘못 로그인 시 즉시 로그아웃 + 에러 메시지

### Owner Mode

```
/                  대시보드 (Owner KPI · 매장 셀렉터 상단)
/staff/*           인력관리 (프로필, 근무표, 출퇴근)
/payroll           급여 정산
/tasks             ⭐ 신규 — 업무 설정 (Owner 관리)
/recipes, /ingredients
/my                매장 정보 + 「매장 계정 만들기」
/my/stores         ⭐ 신규 — 보유 매장 목록 + 「+ 매장 추가」
```

### Store Mode

```
/store/home          매장 홈 — 오늘 업무 진행률 + 출퇴근 현황
/store/tasks         업무 보고 화면 (보고 시 staff 드롭다운 선택)
/store/attendance    출퇴근 펀치 (직원 선택 → 출근/퇴근)
/store/schedule      근무표 (편집 가능 — 본인 매장 한정)
```

매장 단말 운영 흐름:
1. 사장님이 매장 iPad 세팅 시 → 본인 계정으로 「매장 정보」 → 「매장 계정 만들기」(email + 비번 입력) → 매장 계정 생성 + `stores.store_account_user_id` 자동 연결
2. iPad에서 로그아웃 → 매장 계정으로 「매장 로그인」 탭 사용
3. iPad는 이후 매장 계정 세션 유지 (장기 토큰). 새로고침해도 유지
4. 직원들이 출퇴근·업무 보고 시 매번 「누가」 드롭다운으로 staff 선택 (보고자 식별)
5. 비밀번호 변경 필요 시 사장님 화면 → 매장 계정 재발급

## 8. 업무 (Tasks) 기능 — 4단계 분할

### Phase α — 업무 설정 (Owner 화면) · 1.5일
- `/tasks` Owner 페이지 신규
- 업무 CRUD 폼: 카테고리·제목·설명·반복주기
- 카테고리: 오픈·미들·마감·주간·월간·기타
- 반복: 매일 / 매주(요일선택) / 매월(N일) / 1회성

### Phase β — 보고 방식 3종 · 2일
- `report_type` 컬럼 + UI 분기
- **체크 보고** — 단순 ✓ (현재 체크리스트와 동일)
- **메모 보고** — 텍스트 입력
- **사진 보고** — Supabase Storage 업로드 (max 3장, 클라이언트 리사이즈)
- 업무 등록 시 설명 이미지도 첨부 가능 (작업 표준화)

### Phase γ — 대시보드 진행률 + Store Mode 본인 홈 · 1일
- Owner 대시보드: 「오늘의 업무 80% 완료」 카드 + 보고방식별 progress bar
- Store Mode 본인 홈: 위 화면 흐름 7-2 구현
- 「오늘 할 일」 알림 위젯 — 업무 미완료 + 휴무 부족 + 미확정 급여 등

### Phase δ — 캘린더 뷰 + 지각 인디케이터 · 1.5일
- 직원별 일자별 업무 진행 격자
- 출퇴근 데이터 연계 — 「이직원 14:30 지각 1h36m」 표시
- 메모 보고 hover/click 상세 보기

**합계 6일.** β·γ만 묶어도 **3일에 핵심 가치** (보고 + 대시보드 즉시 가치 창출).

## 9. 대시보드 명세

### Owner 대시보드 (`/`)

| 카드 | 내용 | 데이터 출처 |
|---|---|---|
| **오늘 근무 한눈에** | 출근중 N · 미출근 N(이름) · 휴무 N · 지각 N | attendance + month_cells |
| **오늘 업무 진행률** | 80% 완료 + 보고방식별 progress bar + 미완료 명단 | store_task_reports |
| **이번 달 인건비** | 예상 / 확정 / 미정산 N명 | payroll + payByStaff |
| **이번 주 출퇴근 지표** | 출근율 % · 지각 건수 · 평균 실근무 h | attendance 7일 집계 |
| **「오늘 할 일」 알림** | 자동 발견: 휴무 부족·미정산·매장 정보 미입력·근무표 미작성 | 다중 소스 derived |
| **빠른 액션** | 정산 → / 근무표 편집 → / 업무 설정 → | 단순 라우팅 |

### Staff 대시보드 (`/store/me`)
위 화면 흐름 7-2와 동일. 본인 KPI만.

### Manager 대시보드 (`/store/team`)
Owner 대시보드의 「오늘 근무 한눈에」 + 「오늘 업무 진행률」 + 출퇴근 현황 카드만. 인건비·정산은 ✗.

## 10. 다중 매장 (Multi-store) 모델

### 10-1. 데이터 관계
```
auth.users (owner)        auth.users (store account)
     │                            │
     │ owner_id                   │ store_account_user_id
     ▼                            ▼
   stores (N개)  ←─────  매장 1개 = 매장 계정 1개
     │
     ▼ store_id
   [staff, attendance, payroll, schedule_month_cells,
    store_tasks, store_task_reports, ingredients, recipes...]
```

### 10-2. 사용자 스토리보드 (사장님)

**Day 1 — 가입·첫 매장 (Onboarding)**
1. 사장님 회원가입 (이메일/비번)
2. 첫 로그인 → `stores` 카운트 0 → **`/onboarding` 자동 진입** (start 페이지)
3. 매장 정보 입력 폼 (매장명 필수 + 대표자명·사업자번호·주소·연락처 선택)
4. **「매장 추가하기」** → 입력값으로 stores INSERT → `/`(대시보드)
5. (또는) **「건너뛰고 시작」** → 「내 매장」 default 이름으로 INSERT → `/`
6. 이후 로그인부터는 stores ≥ 1 → onboarding 영구 미노출
7. 「내 매장 정보」 → 매장 A 카드의 「매장 계정 만들기」 → email+비번 → 매장 계정 A 생성 (Edge Function 호출 — §10-5)

**Day 7 — 두 번째 매장 오픈**
8. 「내 매장 정보」 페이지 상단 **「+ 매장 추가」** 버튼 → **모달**(onboarding 페이지 재사용 X)
9. 모달: 매장 이름 「젤라또 홍대점」 + 선택 정보 → stores INSERT
10. 매장 B의 「매장 계정 만들기」 → 별도 email/비번 → 매장 계정 B 생성

**Day 8 — 매장 전환**
11. 사이드바 최상단 매장 셀렉터(§10-4): 「젤라또 강남점 ▾」
12. 드롭다운에서 「홍대점」 선택 → 현재 페이지 그대로 유지, **데이터만 홍대점으로 reload**
13. localStorage `gelato-os:active-store-id` = 홍대점 ID

**Day 9 — 매장 단말 (Store account)**
14. 강남점 iPad → 강남점 매장 계정 로그인 → 강남점 데이터만 (RLS 차단)
15. 홍대점 iPad → 홍대점 매장 계정 → 홍대점만. 매장 셀렉터 자체 미노출.

### 10-3. 최초 진입 — Onboarding 페이지 (Phase 0.5)

**원칙**: stores 카운트 = 0 인 사장님만 진입. ≥ 1 되면 영구 미노출.

```
┌─────────────────────────────────────────────────┐
│                                                  │
│              🎉 환영합니다, 사장님!              │
│                                                  │
│  Gelato OS에 오신 것을 환영합니다.              │
│  먼저 매장 정보를 입력해 주세요.                │
│  (입력한 정보는 명세서·세무 서류에 사용됩니다)  │
│                                                  │
│  ──────────────────────────────────             │
│                                                  │
│  매장명 / 상호 *  [젤라또 강남점       ]         │
│  대표자명          [홍길동             ]         │
│  사업자등록번호    [123-45-67890       ]         │
│  매장 주소         [서울시 강남구 ...  ]         │
│  매장 연락처       [02-123-4567        ]         │
│                                                  │

```

**동작**:
- 「매장 추가하기」: 매장명 필수 검증 → 입력값으로 stores INSERT → `/` 이동
- 「건너뛰고 시작」: 「내 매장」 default 이름으로 INSERT → `/` 이동 (사용자가 나중에 MY에서 수정)

**Guard 컴포넌트 패턴**:
```tsx
function OwnerOnboardingGuard({ children }) {
  const { data: stores, isLoading } = useStoreList()
  if (isLoading) return <Loading />
  if ((stores?.length ?? 0) === 0) return <Navigate to="/onboarding" replace />
  return children
}

function OnboardingGate({ children }) {
  const { data: stores } = useStoreList()
  if ((stores?.length ?? 0) > 0) return <Navigate to="/" replace />
  return children
}
```

`useStore` / `ensureStore` 변경:
- 자동 매장 생성 제거 → 0개면 0개 그대로 반환
- 신규 `useStoreList()` 훅 (모든 매장 배열) + `useCreateStore()` 뮤테이션

**두 번째 매장 추가 흐름은 별개**:
- `/my` 페이지에 「+ 매장 추가」 버튼 → 모달 띄움 (Phase 6에서 구현)
- Onboarding 페이지는 「첫 매장」 전용. 모달과 시각·문구 다름.

### 10-5. 매장 계정 생성 — Edge Function (Phase 5)

매장 계정 생성은 Supabase admin API 호출이 필요(`auth.admin.createUser`). 이는 service_role 키가 필요해 **클라이언트에서 직접 호출 불가**.

**Edge Function 설계**:
```
POST /functions/v1/create-store-account
Headers: Authorization: Bearer <사장님 access_token>
Body:    { store_id: uuid, email: string, password: string }

처리:
1. 호출자 Auth 검증 — auth.uid()
2. store_id의 stores row가 owner_id = auth.uid() 인지 검증
3. supabase.auth.admin.createUser({ email, password, app_metadata: { account_type: 'store', store_id }})
4. stores.store_account_user_id = 새 user.id 업데이트
5. 응답 { user_id, email }
```

**Edge Function 미구현 시 임시 우회**:
Supabase 대시보드 → Authentication → Add user에서 수동 생성 + SQL로 `stores.store_account_user_id` 업데이트. 개발 단계에는 OK.

### 10-6. Hooks 변경 영향 + TanStack Query 키

| 항목 | 변경 |
|---|---|
| `useStore()` (단일) | → 첫 store만 반환, **자동 생성 제거** |
| `useStoreList()` (신규) | 사장님 보유 stores 배열 |
| `useActiveStore()` (Phase 6 신규) | localStorage active id 기반 |
| `useCreateStore()` (신규) | 매장 INSERT 뮤테이션 (onboarding + 추가 모달 공용) |
| `ensureStore()` | 더 이상 자동 INSERT 안 함 (deprecated) |
| TanStack Query 키 | 모든 키에 `storeId` 포함 (`['staff', storeId]` 등) → 매장 전환 시 캐시 격리 |
| localStorage | `gelato-os:active-store-id` |

### Hooks 변경 영향
- `useStore()` (단일) → `useActiveStore()` + `useStoreList()`로 분리
- `ensureStore()` → 첫 store 자동 생성 + 추가는 명시적 mutation
- TanStack Query 키에 `storeId` 포함 — 매장 전환 시 캐시 격리

## 13. 미결 사항 (계속 미정)

- 매장 계정 비밀번호 재발급 흐름 — Edge Function으로 admin reset vs 사장님이 새 비번 직접 입력
- 사장님 본인 비밀번호 분실 시 — Supabase 기본 reset 이메일 흐름 사용
- 업무 누적 보고 데이터 보존 기간 — 12개월 vs 3년 (Supabase 용량)
- Task `recurrence` 「격주」 — `recurrence_days` 비트마스크 + 주차 indicator 추가 검토
- 사장님이 「오늘 갑자기 매장 청소」 1회성 업무 즉석 등록 흐름 — `recurrence_type='once'`로 처리
- **푸시 알림 / SMS — 별도 Phase**:
  - 카카오워크 Webhook vs Twilio SMS 선택
  - 트리거: 미출근 직원, 업무 미완료, 사장 OTP 인증 등
- 매장 계정 동시 로그인 제한 — 같은 매장 계정으로 여러 단말 동시 접속 가능 vs 1개로 제한
- 매장 계정 자동 로그아웃 정책 — 무기한 vs N일
