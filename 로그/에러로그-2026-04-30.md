# 에러 로그 — 2026-04-30 (`employment_types` · 로컬 반복 요청)

> 세션 대화 기준 정리. 코드 수정은 동일 날짜 세션에 반영됨.

## 증상

1. **네트워크 탭**: Supabase REST  
   `GET .../rest/v1/employment_types?select=...&store_id=eq.<uuid>&order=code.asc`  
   가 **짧은 간격으로 반복** 호출됨.
2. **로컬 테스트** 시 같은 GET에 **에러**가 나거나, 주소창/직접 REST 호출 시 실패하는 것처럼 보임.

---

## 원인 1: 무한에 가까운 재요청 루프 (프론트)

**흐름 (수정 전)**

1. `useEmploymentTypes()` 가 데이터를 가져오면 `emplTypes`(쿼리 결과)가 갱신됨.
2. `StaffPage` 의 `useEffect` 가 **`emplTypes` 가 바뀔 때마다** `useEnsureDefaultEmploymentTypes().mutateAsync()` 실행.
3. 시드 mutation 의 **`onSuccess` 가 INSERT 여부와 무관하게 항상**  
   `queryClient.invalidateQueries({ queryKey: ['employmentTypes', storeId] })` 호출.
4. 무효화 → `employment_types` 재조회 → 다시 1번 → **2번으로 돌아가 반복**.

삽입할 행이 없을 때도 매번 invalidate 했기 때문에, **성공한 GET 한 번도 끝없이 무효화·재호출**되는 패턴이 됨.

**원인 1b (동일 증상, 별 메커니즘)**  
`useEffect` 의존성에 **`ensureTypes`(mutation 훅이 돌려주는 객체 전체)** 를 넣은 경우, 대부분의 렌더마다 참조가 달라져 effect가 **매 프레임** 실행된다. 이때 `mutateAsync()` → mutationFn 안의 `fetchTypes()`(GET)만 반복해도 네트워크에 **동일 URL이 쉴 새 없이 찍힌다** (invalidate 없이도 가능).

**수정 요약**

| 파일 | 내용 |
|------|------|
| `src/hooks/useEmploymentTypes.ts` | 시드 mutation 이 **실제로 INSERT 가 있었을 때만** `invalidateQueries` (`didInsert`). `useEmploymentTypes` 쿼리에 `staleTime: 60_000`, `refetchOnWindowFocus: false` |
| `src/pages/StaffPage.tsx` | 시드는 **`storeId` 가 생긴 뒤 한 번**만 시도하도록 `useEffect` 의존성에서 `emplTypes` 제거 (루프 차단) |
| `src/pages/StaffPage.tsx` (2차) | `useEffect(..., [storeId, ensureTypes])` 는 **금지** — `ensureTypes` 는 `useMutation()` 반환 객체로 렌더마다 참조가 바뀔 수 있어, effect가 **매 렌더** 실행 → mutation 내부 `fetchTypes()`(GET)만으로도 무한 호출. **`storeId`만 의존** + `useRef`로 매장당 1회 시드만 보장 |

## 원인 2: GET 자체가 실패하는 경우 (API·DB·인증)

브라우저에서 **앱이 붙이는 것과 같이** Authorization 헤더(JWT) 없이 REST URL만 열면, RLS 환경에서 **401 Unauthorized** 등이 정상적으로 발생할 수 있음.

| 가능성 | 확인 |
|--------|------|
| `employment_types` 테이블 없음 | Supabase **Table Editor** 또는 SQL로 존재 확인. 없으면 `supabase/sql/feature3_hr_tables.sql` 실행 |
| 로그인 세션 없음 | 앱은 로그인 후 Supabase 클라이언트가 JWT 를 붙임. 주소창 단독 호출과 동작이 다름 |
| RLS 로 SELECT/INSERT 거부 | 정책이 `stores.owner_id = auth.uid()` 매장 스코프와 일치하는지, 해당 매장 행이 있는지 확인 |

## 확인 순서 (재발 시)

1. 앱에서 **로그인된 상태**로 인력 관리(`/staff`) 진입 후, 네트워크에서 `employment_types` 호출 **횟수·상태 코드** 확인.
2. 반복 호출이 계속이면 **프론트 루프** 의심 → 위 수정 버전인지 확인.
3. **4xx/5xx** 이면 응답 본문 메시지와 함께 테이블 존재·RLS·JWT 여부를 순서대로 점검.

## `staff_default_shifts` 409 / UNIQUE 위반 (동일 요일·동일 시프트 중복)

**증상**  
`POST .../rest/v1/staff_default_shifts?columns=...` (일괄 insert) 시 **동일 `(staff_id, day_of_week, shift)`** 가 두 번 들어가면 PostgreSQL **`unique_violation` (23505)** → REST에서 보통 **409**. (과거에는 `(staff_id, day_of_week)` 만 유일해서 *요일만* 겹쳐도 막혔음 → **정책 변경 후** `(요일, 시프트)` 까지 같을 때만 위반.)

**대응**

1. 저장 전 **폼 규칙 배열에서 `(day_of_week, shift)` 조합 중복** 검사 → `window.alert` + `setFormErr`.
2. 서버에서 동일 제약에 걸린 경우 **`code === '23505'`** 등으로 감지 후 동일 UX.
3. **`getPostgrestMessage`** 로 catch 블록에서 일관되게 문자열화.

**참고 (버그 수정)**  
`handleSave` 끝에 삭제 확인/삭제 mutation 이 붙어 있어 **저장 성공 후 삭제 확인**이 뜨던 문제가 있었음 → **`handleDelete` 별도 함수**로 분리.

**스키마**  
신규: `feature3_hr_tables.sql` 의 UNIQUE `(staff_id, day_of_week, shift)`; 기존 DB: `feature3_staff_default_shifts_unique_dow_shift.sql` 실행.
