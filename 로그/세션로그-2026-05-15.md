## Phase 0 — SQL 마이그레이션 (사용자 직접 적용)

5개 SQL 파일 작성·적용 완료. 누적 신규 컬럼·테이블·정책.

### Phase 0 ⓐ — `feature7_tasks_and_store_accounts.sql`
- `stores.store_account_user_id uuid REFERENCES auth.users(id)` — 매장 계정 연결 컬럼 + 인덱스
- `store_tasks` 테이블 — id/store_id/**category**/title/description/description_images[]/report_type(check|photo|memo)/recurrence_type(daily|weekly|monthly|once)/recurrence_days[]/recurrence_day_of_month/active/display_order/timestamps + 인덱스 + Owner CRUD + Store account READ RLS
- `store_task_reports` 테이블 — id/store_id/task_id/staff_id/work_date/reported_at/checked/memo/photo_urls[] + UNIQUE(task_id, staff_id, work_date) + Owner+Store 풀 RW RLS
- 매장 계정용 RLS 확장 — `attendance`, `schedule_month_cells`, `staff`(R), `stores`(R), `employment_types`(R), `staff_default_shifts`(R), `staff_shift_overrides`(R)
- 체크리스트 테이블 `DEPRECATED` 코멘트 (Phase 7에서 DROP 예정)
- Storage 버킷은 별도 단계로 분리

### Phase 0 ⓑ — `feature7b_task_categories_multi.sql`
- `store_tasks.category text` 단일 → `categories text[]` 다중으로 마이그레이션
- 기존 단일 데이터 `categories = ARRAY[category]` 자동 이관
- CHECK 제약: `cardinality > 0 AND categories <@ ARRAY['open','middle','close','weekly','monthly','other']`
- 이후 ⓓ에서 화이트리스트 제약은 제거됨 (사용자 정의 카테고리 도입)

### Phase 0 ⓒ — `feature7c_task_one_time_date.sql`
- `store_tasks.one_time_date date` 컬럼
- 부분 인덱스: `(store_id, one_time_date) WHERE one_time_date IS NOT NULL`
- CHECK: `recurrence_type='once'` ⟺ `one_time_date IS NOT NULL`

### Phase 0 ⓓ — `feature7d_task_categories_table.sql`
- `task_categories` 테이블 — 매장별 사용자 정의 카테고리 마스터 (id/store_id/code/label/display_order/timestamps + UNIQUE(store_id, code))
- Owner CRUD + Store account READ RLS
- `store_tasks.categories` 화이트리스트 CHECK 제거 → `cardinality > 0`만 강제
- 기존 매장 6종 기본 카테고리(오픈/미들/마감/주간/월간/기타) **자동 백필**

### Phase 0 ⓔ — `feature8_storage_bucket.sql`
- `gelato-tasks` Supabase Storage 버킷 (private, 5MB, JPEG/PNG/WebP)
- `storage.objects` RLS 4종 (SELECT/INSERT/UPDATE/DELETE) — path `tasks/{store_id}/...` 두 번째 폴더가 본인 매장(owner_id 또는 store_account_user_id 매칭)일 때만 허용

## Phase 0.5 — Onboarding 페이지 (코드 구현)

### 동기
기존 `ensureStore`는 첫 로그인 시 「내 매장」 자동 생성 → 사장님이 매장명을 한 번 더 들어가서 수정해야 하는 어색함. 신규 매장 등록 흐름을 명시적 페이지로 분리.

### 구현
- **`src/lib/ensureStore.ts` 리팩토링**:
  - 자동 매장 생성 제거 — 0개면 그대로 0개 반환 (`fetchPrimaryStore` 신규: nullable)
  - `ensureStore` → SELECT only + 없으면 throw (mutation 측 안전 가드)
  - 신규 함수: `fetchStoresForOwner`(배열), `createStoreForOwner`(매장 INSERT)
  - 상수 export: `DEFAULT_STORE_NAME = '내 매장'`
- **`src/hooks/useStore.ts` 확장**:
  - `useStore` queryFn → `fetchPrimaryStore` (자동 생성 안 함)
  - 신규 `useStoreList` (사장 보유 매장 전체)
  - 신규 `useCreateStore` (Onboarding + 「+ 매장 추가」 모달 공용)
- **`src/components/auth/OnboardingGuard.tsx` 신규**:
  - `OwnerOnboardingGuard` — stores.length === 0이면 `/onboarding` 리다이렉트
  - `OnboardingGate` — stores ≥ 1이면 `/onboarding`에서 `/` 리다이렉트 (영구 미노출 보장)
- **`src/pages/OnboardingPage.tsx` 신규**:
  - 환영 메시지 + 5필드 폼 (매장명*, 대표자명, 사업자번호, 주소, 연락처)
  - 사업자번호 자동 「-」 포매팅 + 10자리 검증
  - 전화번호 자동 포매팅 (02/지역/모바일 분기)
  - 「매장 추가하기」 — 입력값으로 매장 생성
  - 「건너뛰고 시작」 — 「내 매장」 기본명으로 생성
- **`src/App.tsx`**: `/onboarding` 라우트 + 기존 라우트에 `<OwnerOnboardingGuard>` 래핑

### 동작
```
신규 사장 가입 → 로그인 → stores 0 → /onboarding 자동 진입
  ├─ 매장 추가하기 → INSERT → /
  └─ 건너뛰고 시작 → 「내 매장」 INSERT → /
이후 stores ≥ 1 → /onboarding 영구 미노출
기존 사장은 매장 1개 보유 → 아무 영향 없음
```

## Phase 2 — 보고 방식 인프라 + Supabase Storage

### 2-1. Storage 인프라
- **`src/lib/imageUpload.ts` 신규**:
  - `resizeImage(file, maxDim=1024)` — Canvas 기반, JPEG q=0.82 압축
  - `uploadTaskImage(file, storeId)` → `tasks/{storeId}/{timestamp}-{rand}.jpg` 경로 반환
  - `deleteTaskImages(paths)` 배치 삭제
  - `getSignedUrl(path)` / `getSignedUrls(paths)` — 1시간 만료
- **`src/hooks/useSignedUrls.ts` 신규** — TanStack Query 캐싱 (50분 staleTime, 자동 refetch)

### 2-2. 업무 설명 이미지 (`description_images`)
- TaskForm: 최대 3장 업로드 UI (점선 「+ 사진 추가」 버튼 + 썸네일 그리드)
- TaskCard: 썸네일 strip (있을 때만)
- 클라이언트 리사이즈 후 즉시 storage 업로드

### 2-3. 취소·삭제 시 cleanup (사용자 후속 요청)
- **ImgItem 모델로 리팩토링**: `{ kind: 'existing'|'added', path, removed }`
- ✕ 클릭 = `removed=true` 마크만 (storage 즉시 삭제 ❌)
- **Unmount cleanup** (취소·모달 X·오버레이 클릭·라우트 이동 모두 커버):
  - `submittedRef.current === false` → 이번 폼 세션에서 추가된 (`kind='added'`) orphan 일괄 삭제
- **Submit 성공 시**:
  - final paths = `removed=false` 항목 → task UPDATE
  - 제거된 paths (existing 의도적 삭제 + added 후 제거) → storage cleanup
  - `submittedRef.current = true` → unmount 시 추가 cleanup 안 함
- **업무 row 삭제 시**: `useDeleteStoreTask`가 row 삭제 전 `description_images` 조회 → row 삭제 → storage cleanup (best-effort)

| 시나리오 | 동작 |
|---|---|
| 새 폼에서 사진 2장 업로드 → 취소 | 2장 모두 storage 삭제 ✓ |
| 기존 사진 ✕ → 취소 | task·storage 모두 그대로 ✓ |
| 기존 사진 ✕ → 저장 | task에서 빠지고 storage에서도 삭제 ✓ |
| 카드 「삭제」 | task row + 모든 이미지 삭제 ✓ |

3. **업무 보고** (`/store/tasks`) — 카테고리별 그룹 + 보고자 드롭다운 + report_type별 분기 UI (체크박스 / 사진 업로드 / 메모 입력)
4. **근무표** (`/store/schedule`) — 기존 월간 근무표 컴포넌트 재사용 (편집 가능 분기)
5. **Owner 대시보드** (`/`) — 오늘 근무 한눈에 + 오늘 업무 진행률 + 이번 달 인건비 + 알림 카드

### 우선순위 2 — Phase 5 (매장 계정 자동 발급)
6. **Edge Function** `create-store-account` — owner access token 검증 + admin API로 user 생성 (`app_metadata.account_type='store'`) + `stores.store_account_user_id` UPDATE
7. **MyPage 「매장 계정 만들기」 모달** — email/password 입력 → Edge Function 호출 → 생성된 계정 정보 표시 + 비번 재발급

### 우선순위 3 — Phase 6 (다중 매장)
8. **`useActiveStore`** 훅 — localStorage `gelato-os:active-store-id` 기반
9. **사이드바 매장 셀렉터** — 로고 아래 「🏪 매장명 ▾」 드롭다운 + 「+ 매장 추가」 모달
10. **모든 hooks 쿼리 키에 storeId 포함** — 매장 전환 시 캐시 격리
11. **MyPage → MyStoresPage** 분리 검토 (매장 N개 카드 grid + 매장 정보 편집 sub-page)

### 우선순위 4 — Phase 7 (정리)
