### 2. 아키텍처 설계 (`설계-2026-04-27.md`)
오늘 세션의 핵심 산출물. 아래 내용을 결정하고 문서화했다.

**DB 스키마 결정 사항**
- Feature 1 구현 테이블 6개 확정: `stores`, `ingredients`, `recipes`, `recipe_ingredients`, `flavors`, `production_logs`
- Feature 2~4 테이블 스키마도 미리 설계 완료 (구현은 나중에)
- `store_id`를 모든 테이블에 처음부터 추가하기로 확정
- `ingredients` 테이블이 Feature 1(레시피 원가 계산)과 Feature 2(재고 관리)에서 공유됨을 확인
- `production_logs`가 Feature 1-2 연동의 다리 역할임을 확인

**프론트엔드 구조 결정 사항**
- 서버 상태: TanStack Query (hooks/ 폴더로 분리)
- 로컬 상태: Zustand (폼 임시 저장 용도만)
- 원가 계산: DB 조회 없이 프론트 순수 함수로 처리 (`CostCalculator.tsx`)
- 페이지 구조: `recipes/`, `flavors/`, `production/` (Feature 1), 나머지는 폴더만 생성

**RLS 정책 패턴 결정**
- 모든 테이블에 동일한 패턴 적용
- `stores` 테이블: `owner_id = auth.uid()`
- 나머지 테이블: `store_id IN (SELECT id FROM stores WHERE owner_id = auth.uid())`

### 3. 주요 결정 맥락
- 자산관리앱은 HTML 프로토타입 존재 + 1인용 → 프론트 먼저
- 가게운영앱은 멀티유저 SaaS 설계 + 데이터 정합성 중요 → DB/백엔드 먼저
- 이 판단을 기반으로 개발 순서를 DB 설계 → Auth → 재료 CRUD → 레시피 CRUD → 메뉴판 → 생산기록 순으로 확정
