## 증상

1. 출퇴근 탭 > 오늘 섹션에서 **«출근» 버튼을 눌러도** 직원 카드의 "실제" 행이 "출퇴근 기록 없음"으로 유지됨.
2. 주간 저장 시 자동 생성된 기준 출퇴근 기록이 DB에 있음에도 "실제" 행에 **아무 데이터도 표시되지 않음**.
3. "실제" 시각이 없으면 **«수정» 링크가 노출되지 않음** → 수기 수정 기능도 사용 불가.

## 관련 데이터 구조 (배경)

`attendance` 테이블 하나에 두 종류의 레코드가 공존한다.

| 구분 | `is_baseline` | 생성 시점 | 생성 함수 |
|------|:---:|---|---|
| 기준 레코드 | `true` | 주간 근무표 «저장» 클릭 시 자동 생성 | `generateAttendanceBaselineForWeek` |
| 실적 레코드 | `false` | «출근»·«퇴근» 버튼 클릭 시 생성 | `usePunchIn` / `usePunchOut` |

`groupAttendanceByDateStaff`는 이 둘을 분리하여 `StaffDayBlock` 타입으로 묶는다.

```ts
type StaffDayBlock = {
  staff_id: string
  staff_name: string
  baseline?: AttendanceRow   // is_baseline: true
  actual?: AttendanceRow     // is_baseline: false (pickActual 결과)
}
```

## 원인 1: 기준 레코드가 "실제" 행에 표시되지 않음 (주요 원인)

**흐름 (수정 전)**

1. 주간 근무표를 저장하면 `generateAttendanceBaselineForWeek`가 `attendance`에 `is_baseline: true` 레코드를 자동 삽입.
2. `groupAttendanceByDateStaff`에서 `is_baseline: true` → `block.baseline`, `is_baseline: false` → `block.actuals`로 분리.
3. `PersonBlock`은 `block.actual` (= `pickActual(block.actuals)`)만 "실제" 행에 렌더링.
4. 실적 레코드가 하나도 없으면 `block.actual === undefined` → `actualIn = null` → "출퇴근 기록 없음".

**결과**: 기준 레코드가 DB에 있어도 "실제" 행에는 표시되지 않고, «수정» 버튼 조건(`actualIn !== null`)도 충족되지 않아 수정 자체가 불가능했다.

**수정**

```ts
// 수정 전
const actualIn = block?.actual?.check_in ?? null   // 실적 레코드만 참조

// 수정 후
const actualRecord  = block?.actual ?? null
const displayRecord = actualRecord ?? block?.baseline ?? null  // 기준 레코드 폴백
const isBaseline    = displayRecord?.is_baseline ?? false
const displayIn     = displayRecord?.check_in ?? null
const displayId     = displayRecord?.id ?? null
```

- **실적 레코드**가 있으면 그것을 표시 (우선).
- 없으면 **기준 레코드**를 폴백으로 표시하고 `(기준)` 배지를 붙임.
- 어느 쪽이든 `displayIn`이 설정되어 있으면 «수정» 버튼 노출.

## 원인 2: 출근·퇴근 버튼 상태 오류

**흐름 (수정 전)**

- «출근» 버튼: `disabled={punchIn.isPending || Boolean(actualIn)}`
- «퇴근» 버튼: `disabled={punchOut.isPending || !actualIn || Boolean(actualOut)}`
- `actualIn`이 기준 레코드의 `check_in`을 참조하게 될 경우, **기준 레코드만 있어도 «출근» 버튼이 비활성**될 위험이 있었음.

**수정**

버튼 상태는 **실적 레코드**(`is_baseline: false`)만 기준으로 판단하도록 분리.

```ts
// 버튼 제어는 실적 레코드 기준만 사용 (기준 레코드가 버튼 상태에 영향 없음)
const hasActualPunchIn  = Boolean(actualRecord?.check_in)
const hasActualPunchOut = Boolean(actualRecord?.check_out)

// 출근: disabled={punchIn.isPending  || hasActualPunchIn}
// 퇴근: disabled={punchOut.isPending || !hasActualPunchIn || hasActualPunchOut}
```

## 원인 3: `findOpenAttendanceToday`가 기준 레코드를 오검출

**흐름 (수정 전)**

```ts
const { data } = await supabase
  .from('attendance')
  .select('id, check_out')
  .eq('store_id', storeId)
  .eq('staff_id', staffId)
  // is_baseline 필터 없음
  .gte('check_in', start.toISOString())
  .lt('check_in', end.toISOString())
```

- `is_baseline` 필터 없이 오늘 범위 안의 **모든** 레코드를 조회.
- 기준 레코드(`is_baseline: true`)는 정상적으로 `check_out`이 설정되지만, 만약 어떤 이유로 `check_out = null`인 기준 레코드가 존재하면 `findOpenAttendanceToday`가 이를 반환 → 실적 레코드가 없음에도 **"이미 출근 처리된 기록이 있습니다."** 에러 발생.

**수정**

```ts
.eq('is_baseline', false)  // 실적 레코드만 검색
```

## 원인 4: 쿼리 무효화가 에러 경로에서 누락

**흐름 (수정 전)**

```ts
async function handlePunchIn() {
  try {
    await punchIn.mutateAsync(staffId)
    void queryClient.invalidateQueries({ queryKey: ['attendance'] })  // 성공 시만 실행
  } catch (e) {
    setPunchError(...)  // 에러 시 invalidate 호출 없음
  }
}
```

- 출근 버튼을 처음 클릭해 레코드가 생성됐지만 쿼리 갱신이 누락된 경우, UI는 "출퇴근 기록 없음"을 계속 표시.
- 두 번째 클릭 → `findOpenAttendanceToday`가 기존 레코드를 찾아 에러 throw → catch 블록 진입 → `invalidateQueries` 호출 없음 → UI는 여전히 구버전 데이터 유지.
- 결과: **에러 메시지("이미 출근 처리된 기록이 있습니다.")는 표시되지만, "실제" 행은 "출퇴근 기록 없음"으로 유지**되는 모순된 화면.

**수정**

```ts
async function handlePunchIn() {
  try {
    await punchIn.mutateAsync(staffId)
  } catch (e) {
    setPunchError(...)
  } finally {
    void queryClient.invalidateQueries({ queryKey: ['attendance'] })  // 성공·실패 모두 실행
  }
}
```

`finally` 블록 이동으로 성공·실패 여부와 무관하게 항상 최신 데이터를 조회.

## 원인 5: 쿼리 무효화 범위 부족

**흐름 (수정 전)**

`usePunchIn.onSuccess`에서 `queryClient.invalidateQueries({ queryKey: ['attendance', storeId] })` 를 호출했다. `storeId`는 `usePunchIn` 훅이 호출될 당시의 `useStore()` 결과이므로, 렌더 시점에 따라 `useAttendanceList`가 사용하는 키 `['attendance', storeId, filters]`와 storeId가 불일치할 가능성이 있었다.

**수정**

`PersonBlock`의 `handlePunchIn` / `handlePunchOut`에서 mutation 성공 후 추가로 **더 넓은 범위의 무효화**를 직접 호출.

```ts
await punchIn.mutateAsync(staffId)
void queryClient.invalidateQueries({ queryKey: ['attendance'] })  // 전체 attendance 키 무효화
```

## 추가 픽스 (재발) — 출근 INSERT 후 화면 미갱신·"이미 출근 처리된 기록" 에러만 노출

### 증상 (재발)

- 출근 버튼 클릭 → DB에는 `is_baseline=false, check_out=null` 실적 레코드가 INSERT 됨.
- 그러나 카드의 «실제» 행은 여전히 **"출퇴근 기록 없음"**.
- 두 번째 출근 클릭 시 `findOpenAttendanceToday`가 그 레코드를 찾아 **"이미 출근 처리된 기록이 있습니다."** 에러만 표시.
- 결과: 화면상 출근 기록이 안 보이고, 퇴근 버튼은 `hasActualPunchIn=false` 판정으로 비활성 유지.

### 원인 분석

1. `usePunchIn.onSuccess`의 `invalidateQueries({queryKey:['attendance', storeId]})` 가 동기적으로 호출되어 refetch 완료를 기다리지 않음 → UI 갱신 타이밍이 어긋남.
2. `useAttendanceList` 의 기본 staleTime/refetchOnMount 설정으로 캐시된 결과가 즉시 갱신되지 않을 수 있음.
3. `fetchAttendance` 의 `from/to` 가 `\`${ymd}T00:00:00\`` (timezone 미지정) 으로 들어가 `timestamptz` 컬럼과 비교 시 UTC 로 해석 → 한국시간 09:00 이전 출근분이 누락되는 경계 케이스.
4. `limit(200)` 한도로 누적 데이터가 쌓이면 오늘 분이 잘려나갈 위험.

### 수정

| 파일 | 변경 내용 |
|------|-----------|
| `src/hooks/useAttendance.ts` | `useAttendanceList` 에 `staleTime: 0`, `refetchOnMount: 'always'`, `refetchOnWindowFocus: true` 추가 |
| `src/hooks/useAttendance.ts` | `usePunchIn`/`usePunchOut`/`useCorrectAttendance` 의 `onSuccess` 를 `async` 로 변경, `await invalidateQueries({queryKey:['attendance'], refetchType:'active'})` 로 refetch 완료까지 대기 |
| `src/hooks/useAttendance.ts` | `fetchAttendance` 의 `from/to` 를 로컬 자정 → ISO(UTC) 로 변환(`ymdToLocalIsoStart/End`) 하여 timestamptz 비교 정확도 확보 |
| `src/hooks/useAttendance.ts` | `order('check_in', {nullsFirst:false})`, `limit(500)` 으로 누락 방지 |
| `src/pages/StaffPage.tsx` | `handlePunchIn`/`handlePunchOut` 의 `finally` invalidate 를 `await` + `refetchType:'active'` 로 강화 |

### 확인 순서

1. 출근 버튼 클릭 → 카드 «실제» 에 `HH:MM (출근) ~ [퇴근 전]` 즉시 표시되는지 확인.
2. 퇴근 버튼이 활성으로 전환되는지 확인.
3. 퇴근 버튼 클릭 → `~ HH:MM (퇴근)` 추가 표시되는지 확인.

## 추가 픽스 — 미래 날짜에서 baseline이 「실제 출퇴근」으로 노출되는 문제

### 증상

- 출퇴근 탭의 «날짜 이동»으로 **미래 날짜**(예: 내일·다음주)를 선택하면, 실제 출퇴근 기록이 없는데도 «실제» 행에 예정과 동일한 시각이 표시됨.
- 마치 "DB가 자동으로 미래 출퇴근을 미리 찍어둔" 것처럼 보임.

### 원인

`PersonBlock`은 실적이 없을 때 baseline(`is_baseline=true`)을 폴백으로 「실제」 행에 표시하도록 되어 있다. 이 로직은 **과거 실적이 누락됐을 때 예정값을 안내**하려는 의도였지만, baseline은 주간 근무표 «저장» 시 미래 날짜분까지 한꺼번에 INSERT 되므로 **미래 날짜에서도 폴백이 적중**한다.

추가로 `displayId`가 baseline의 `id`도 가리키고 있어, 사용자가 «수정»을 누르면 **baseline 레코드 자체가 수기수정됨 → 예정 데이터 오염** 위험까지 있었다.

### 수정

`src/pages/StaffPage.tsx — PersonBlock`

| 항목 | 변경 |
|------|------|
| `allowBaselineFallback` | `!isFuture && !actualRecord` 일 때만 baseline 폴백 허용 (`isFuture = dateKey > formatYmdLocal(new Date())`) |
| `displayId` | 항상 `actualRecord?.id` 만 가리키도록 변경. baseline 은 «수정» 대상에서 완전히 제외 |
| `pd` / `isOver` / `statusLabel` | 비교 대상을 `displayRecord` → `actualRecord` 로 좁힘. baseline 폴백에는 지각/조기/초과/정상 라벨 미적용 |
| 「(기준)」 캡션 | 「(예정 · 출퇴근 전)」 으로 문구 변경 — 사용자에게 baseline 임을 명확히 전달 |

### 결과

- 미래 날짜: «실제» 행에 baseline 시각이 더 이상 표시되지 않음. 「출퇴근 기록 없음」 으로 표시.
- 과거 날짜에서 실적이 누락됐을 때만 baseline 폴백 표시(`(예정 · 출퇴근 전)` 캡션 동반).
- baseline 만 있는 상태에서는 «수정» 버튼이 비활성. 수기수정으로 예정 데이터가 오염될 경로 차단.

### 확인 순서

1. 출퇴근 탭에서 「날짜 이동 → 내일 날짜」 선택 → 직원 카드 «실제» 행이 「출퇴근 기록 없음」 으로 표시되는지.
2. 같은 카드의 «수정» 버튼이 비활성 상태인지.
3. 오늘 출근 버튼 클릭 후 정상적으로 시각이 chip 으로 표시되는지(상태 라벨도 함께).
4. 과거 날짜로 이동했을 때 실적이 없는 직원 카드는 「(예정 · 출퇴근 전)」 캡션과 함께 baseline 시각이 표시되는지.
